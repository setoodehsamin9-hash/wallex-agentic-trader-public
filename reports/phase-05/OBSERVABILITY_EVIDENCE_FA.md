این وضعیت فقط مربوط به لایهٔ گزارش و شواهد است؛ اعلام سودآوری یا آمادگی LIVE نیست.

## چه چیزی ساخته شد؟

- خوانندهٔ canonical برای یک run از SQLite: محیط، اختیار، زمان شواهد، مدل، نمادها، پوزیشن/سفارش،
  سود و زیان، کارمزد، بازده، افت حساب، فعالیت، Risk، مدل، خبر و بازیابی را از دادهٔ ذخیره‌شده گزارش می‌کند.
- برای جلوگیری از ایجاد فایل جانبی کنار مبدأ، DB و WAL دو بار با بایت‌های یکسان خوانده می‌شوند و SQLite فقط
  روی کپی موقت باز می‌شود. اگر فایل حین برداشت تغییر کند، مشاهده با خطای صریح متوقف می‌شود و باید دوباره اجرا شود.
- بازسازی دفتر مالی از رخدادهای یکتای FILL: مقدار تجمعی سفارش هرگز دوباره به‌عنوان معامله جمع زده نمی‌شود.
  زنجیرهٔ هش، ترتیب seq، checkpoint و معاملات بسته‌شده با نتیجهٔ بازسازی تطبیق داده می‌شوند.
- CLI کوتاه فارسی، گزارش KPI فارسی و خروجی دمو با همان دلیل کوتاه ذخیره‌شده؛ هیچ توضیح تازه‌ای با مدل تولید نمی‌شود.
- بستهٔ شواهد با ترتیب ثابت، هش هر فایل، مشخصات تکرارپذیری و قابلیت بازسازی آفلاین نتیجهٔ مشاهده.

فقط `src/wallex_agent/observability/`، ثبت فرمان‌های خواندنی در `interface/cli.py`، تست‌ها و گزارش‌ها اضافه/تغییر کردند.
هیچ dependency یا schema جدیدی به مسیر معامله اضافه نشده است.

## استفاده

```bash
uv run wallex-agent status RUN_ID --db state.sqlite
uv run wallex-agent performance RUN_ID --db backtest.sqlite
uv run wallex-agent explain RUN_ID --last 5 --db state.sqlite
uv run wallex-agent demo-evidence RUN_ID --db state.sqlite
uv run wallex-agent evidence export RUN_ID --db state.sqlite --out evidence/RUN_ID
uv run wallex-agent evidence verify evidence/RUN_ID
```

`--db` نسبی زیر `WALLEX_AGENT_STATE_DIR` (پیش‌فرض `var/`) خوانده می‌شود؛ مسیر مطلق نیز مجاز است.
قالب قدیمی `status --run-id RUN_ID` حفظ شده است. پوشهٔ خروجی موجود بازنویسی نمی‌شود.
برای خروجی بایت‌به‌بایت یکسان، به export زمان UTC ثابت با `--generated-at` بدهید.

## معنی اعداد

«محقق‌شده» یعنی سود/ضرر فروش‌های ثبت‌شده به تومان؛ «باز» یعنی سود/ضرر دارایی باقی‌مانده.
«خالص» تفاوت ارزش حساب و سرمایه شروع است. کارمزد از قبل داخل مبنای هزینه لحاظ شده و بار دوم کم نمی‌شود.
«افت از قله» کاهش ارزش حساب نسبت به بیشترین ارزش قبلی است. «نسبت سود به زیان» مجموع سود معاملات سودده
تقسیم بر قدرمطلق زیان معاملات زیان‌ده است؛ اگر زیانی نباشد، نسبت تعریف‌نشده می‌ماند.

صفر با نامعلوم متفاوت است: مقدار غایب `null` یا «نامعلوم/ناموجود» می‌ماند. بدون معاملهٔ بسته، درصد موفقیت
و میانگین معامله تعریف نمی‌شوند. بدون mark/وضعیت تازهٔ ثبت‌شده، برای پوزیشن باز قیمت یا exposure حدس زده نمی‌شود.
ارزش‌گذاری‌های فعلی journal معمولاً تا یک تومان گرد شده‌اند؛ نقد، سود محقق و کارمزد از FILLها دقیق بازسازی می‌شوند.
ارزش‌گذاری هم‌زمان با fill، بدون شاهدِ ترتیب، ممکن است قبل از آن بوده باشد؛ در این حالت ارزش/سود باز نامعلوم می‌ماند.
جدول غایب نیز به صفرِ فراخوانی/شکست مدل، Risk یا خطای اجرا تبدیل نمی‌شود.

هر گزارش فقط یک run دارد. BACKTEST و SHADOW شبیه‌سازی‌اند؛ LIVE جداست و سود/ضرر آن با شبیه‌سازی جمع نمی‌شود.
سلامت CLI وضعیت **ثبت‌شده** است، با زمان آخرین شاهد؛ سالم بودن لحظه‌ایِ فرایند یا موجودی فعلی صرافی را ادعا نمی‌کند.
کلید قطع سراسریِ فعلی به run تاریخی نسبت داده نمی‌شود؛ فقط شاهد مخصوص همان run قابل گزارش است.

## شمارش نوشتن واقعی والکس

`real_wallex_write_count` ورودی دستی نمی‌پذیرد.

- برای صفرِ BACKTEST/SHADOW باید ORDER/STATEهای زنجیره با رخدادهای اجرای دارای منبع همان شبیه‌ساز
  تطبیق داشته باشند و هر سفارش، SUBMITTING ثبت‌شده داشته باشد.
- نام محیط به‌تنهایی، جدول خالی یا یک عدد صفر دستی هیچ‌کدام اثبات نیستند؛ پاسخ `UNKNOWN` است.
- رخدادهای فعلی LIVE همهٔ نوشتن‌ها، مخصوصاً لغو سفارش را audit نمی‌کنند؛ شمارش کامل LIVE عمداً `UNKNOWN` است.
  تعداد ارسال‌های EXCHANGE مشاهده‌شده جداگانه گزارش می‌شود و جای شمارش همهٔ نوشتن‌ها نیست.
- شمارش مربوط به پیشوند ثبت‌شدهٔ journal است؛ زنجیرهٔ سالم، نبودِ یک رخداد ثبت‌نشده در انتهای اجرا را ثابت نمی‌کند.

این محدودیت با تغییر Execution برطرف نشد، چون خارج از مالکیت این شاخه است. جزئیات برای کلود در handoff آمده است.

## نتیجهٔ نهایی آزمون‌ها

**PASS:** pytest کامل ۵۰۴ passed، دو skipped و دو deselected؛ Pyright strict بدون خطا؛ اسکن secret بدون finding.
بازبینی مستقل یک‌بار انجام شد و هر پنج ایراد مهم با تست RED→GREEN اصلاح شد. در smoke نهایی نیز قالب دمو
با context واقعیِ runtime اصلاح و پس از آن تست کامل و Pyright دوباره سبز شد.

دو بستهٔ شبیه‌سازی محلی در `var/observability-final-gate/backtest-take-1/` و `shadow-take-1/` باقی مانده‌اند:
هرکدام ۱۶ فایل، تطابق کامل خروجی API/CLI، بازسازی یکسان و شمارش نوشتن واقعی صفر دارند.
این ورودی‌ها **synthetic fixture** هستند، نه شواهد سودآوری بازار یا نتیجهٔ مسابقه. مسیرها و هش‌های دقیق در فایل verification ثبت شده‌اند.
